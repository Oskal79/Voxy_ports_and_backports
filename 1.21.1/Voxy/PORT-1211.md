# Voxy → Minecraft 1.21.1 / NeoForge — port in progress

Working tree: `voxy-1211/` (copied from the finished 26.1.2 port in `voxy/`, which is untouched).

```bash
./.buildenv/scripts/gradlew-container-jdk21.sh voxy-1211 compileJava   # JDK 21 container
```

Target: MC **1.21.1**, NeoForge **21.1.248**, Java **21**, against the mods you run —
Sodium **0.8.13-beta.2** (`.buildenv/ref-sodium/sodium-1.21.1-0.8.13-beta.2.jar`) and
Iris **1.8.14-beta.1** (`.buildenv/iris-1.21.1-1.8.14-beta.1.jar`).

## Why this is a big port

Voxy has **never** supported 1.21.1 — upstream releases jump 1.20.4 → 1.21.6, and the oldest
modern branch is 1.21.5. Going to 1.21.1 means crossing the 1.21.5/1.21.6 rendering rewrite
backwards: the whole `com.mojang.blaze3d.opengl` package (`GlBuffer`, `GlCommandEncoder`,
`GlRenderPass`, `GlDebug`) and the GPU abstraction (`GpuDevice`, `GpuTexture`, `GpuBufferSlice`,
`GpuSampler`) simply do not exist in 1.21.1.

Mitigating factor: voxy's core is raw LWJGL GL, so the damage is concentrated in the
Minecraft-integration seams rather than spread through the renderer.

The injector check earned its keep here: the build compiled cleanly while **7 mixins would still have
failed to bind at runtime**. Those were only visible by checking `@At` targets against real bytecode:

* `Minecraft.disconnect` is `(Screen, boolean)` on 1.21.1, not `(Screen, boolean, boolean)`
* `BlockableEventLoop` has no `isNonRecoverable(Throwable)` — the crash-on-load-error hook now wraps
  the `Runnable.run()` call instead, which is independent of how the catch block is written
* `Minecraft.<init>` never calls `Options#save()` on 1.21.1 — GPU-selector hook moved to HEAD, still
  before the window and GL context exist
* Sodium 0.8.13's `PendingSectionMeshUpload` has **no fade-time argument**, so the mesh-fade-cancel
  mixin had nothing to modify and was removed outright
* `RenderSectionManager` has no `renderOutOfGraph` / `readRenderListFromTree`; the visible-stream
  reset moved into `SectionCollector`'s constructor, which is where 0.8.13 starts a visibility pass
* Iris 1.8.14's `beginLevelRendering()` has no `_activeTexture` call to anchor to — HEAD is early enough

### Iris cluster (last to fall)

* `addDynamicSampler`/`addDefaultSampler` take a `GlSampler` directly in 1.8.14, not a `Supplier<GlSampler>`;
  the constant is `MIPPED_NEAREST` (the `_NEAREST_NEAREST` naming is newer Iris)
* `com.google.gson.Strictness` is Gson 2.11+; 1.21.1 ships 2.10.1, so `setLenient()`
* `MixinLevelRenderer` — 1.21.1's `renderLevel(DeltaTracker, boolean, Camera, GameRenderer,
  LightTexture, Matrix4f frustum, Matrix4f projection)` hands over the camera and both matrices
  directly, so this ended up *simpler* than the 26.x render-state bundle it replaced

## Fixed after the first launch attempt

**Crash: `FindException: Module org.lwjgl.lmdb not found, required by org.lwjgl.lmdb.natives`**
(boot module layer, before Mixin init — nothing in `latest.log`, only in the launcher console).

LWJGL's lmdb/zstd jars are multi-release and carry `META-INF/versions/9/module-info.class`:

```
module org.lwjgl.lmdb.natives { requires transitive org.lwjgl.lmdb; }
module org.lwjgl.lmdb         { requires transitive org.lwjgl;      }   <- LWJGL core
```

On NeoForge 21.1 Minecraft's LWJGL core lives on the **classpath**, not the module path, so
`org.lwjgl` is not a resolvable module and the whole chain fails. Compounding it, the windows and
linux natives jars declare the **same module name**, which is a duplicate within one layer.
(The 26.1.2 build ships the same six jars and is unaffected — that NeoForge line puts LWJGL on the
module path, which is why this only bit on 1.21.1.)

Fix: `stripLwjglModuleInfo` drops the module descriptors from the six jar-in-jar LWJGL jars, making
them automatic modules that require nothing. Classes and native payloads are untouched, and LWJGL's
`SharedLibraryLoader` finds the natives on the classpath exactly as before.

Checked the other five embedded jars too — `commons-pool2`, `sqlite-jdbc` and `xz` declare modules
but only require JDK modules plus `static` (optional) ones, so they resolve fine; they are also
byte-identical to the working 26.1.2 build.

**Crash 2: `ResolutionException: Module yabn reads more than one module named org.lz4.java`**

Minecraft 1.21.1 already ships `org.lz4:lz4-java:1.8.0` as a *game library*, so embedding a second
copy puts two modules of the same name in the boot layer. Voxy now takes it as `compileOnly` on this
target and uses the game's copy (same version, identical API). 26.x dropped lz4 from the game
libraries, which is why the 26.1.2 build still embeds it.

Checked every other embedded library against the pack and the game classpath: voxy is the sole
provider of each, and only `lz4-java` and LWJGL core are game libraries.

**Crash 3: `@Inject handler before super() invocation must be static` (MixinGPUSelect)**

Self-inflicted. When 1.21.1's `Minecraft` constructor turned out not to call `Options#save()`, this
hook was moved to `@At("HEAD")` of `<init>` -- which is *before* `super()`, where `this` does not
exist, so Mixin requires a **static** handler. The handler touches no instance state, so it is now
static. It is the only constructor-HEAD injection in the mod; every other `<init>` inject uses
RETURN/TAIL/INVOKE, all of which run after `super()`.

`VerifyInjections.java` now enforces this rule (`@At("HEAD")` on `<init>` => handler must be static).
Verified it reproduces the crash against the old jar and passes against the fixed one.

**Crash 4: `Invalid descriptor on MixinWorld->@Inject::voxy$injectIdentifier`**

The first failure from the *port itself* rather than packaging. An `@Inject` handler's parameters
must mirror the target method's exactly, and 1.21.1's `Level` constructor takes a
`Supplier<ProfilerFiller>` that 26.x does not:

```
expected (WritableLevelData, ResourceKey, RegistryAccess, Holder, Supplier, ZZJI, CallbackInfo)
found    (WritableLevelData, ResourceKey, RegistryAccess, Holder,           ZZJI, CallbackInfo)
```

`VerifyInjections.java` now checks handler parameters against the target for every `@Inject`. Adding
that check immediately surfaced a **second, not-yet-hit instance**: `MixinClientLevel`, whose handler
was missing the same profiler `Supplier` *and* carried a trailing `seaLevel` int that 1.21.1's
`ClientLevel` constructor does not have. Both are fixed; that one would have been the next crash.

**Crash 5: `non-static callback method GlDebug::voxy$wrapDebug targets a static method`**

`GlDebug#printDebugLog` is static in 1.21.1, and Mixin requires a callback targeting a static method
to be static itself. Handler and its two helpers are now static.

### The verifier now checks

1. `@Mixin` target class exists on the real classpath
2. the `method` selector resolves (name **and** descriptor)
3. the `@At(INVOKE/FIELD)` target is actually referenced in that method's bytecode
4. `@Inject` handler parameters mirror the target's
5. a callback targeting a **static** method is itself static (any injector kind)
6. `@At("HEAD")` on `<init>` has a static handler (special case: runs before `super()`)

Checks 3-6 each caught a real crash that compiling did not, and check 4 additionally pre-empted one.
Both the 1.21.1 jar and the known-good 26.1.2 jar pass all six.

> Note for future debugging: `latest.log` does **not** capture boot-layer failures. Every one of
> these exceptions appeared only in PrismLauncher's console output.

## In-game issues found after it booted

**0. ROOT CAUSE of every in-game symptom: LWJGL natives could not load**

```
UnsatisfiedLinkError: Failed to locate library: liblwjgl_zstd.so
  at ZSTDCompressor.compress -> Service.runJob -> Block.acquire
```

Self-inflicted, two fixes back. Stripping `META-INF/versions/9/module-info.class` from the LWJGL
jars solved the boot-layer `FindException`, but those descriptors also carried
`opens <os>.<arch>.org.lwjgl.<lib>`, which is how LWJGL locates the native payload. Without it the
lookup fails across the split base/natives modules.

Every section-compress job then threw `NoClassDefFoundError`, which propagated out of
`Service.runJob` and **killed the worker thread**. That single fault produced all three symptoms:

* no `Dedicated Voxy Worker` threads survive -> nothing builds -> no LoD
* with "use sodium threads" ON, Sodium's own `Chunk Render Task Executor` threads die the same way
  -> vanilla terrain stops rendering too
* `SectionSavingService.shutdown -> blockTillEmpty` waits on a queue with no drainer -> exit hangs

Fix: keep stripping the module descriptors (still needed for the boot layer) but **copy the native
payloads into each library's own jar**, so LWJGL's lookup stays within one module. Verified in the
built jar: `lwjgl-zstd-3.3.3.jar` now carries both `liblwjgl_zstd.so` and `lwjgl_zstd.dll` alongside
its 41 classes, and likewise for lmdb.

Found only after building a minimal instance (1.21.1 + NeoForge + Sodium + voxy). The 700-mod pack's
25k-line logs had hidden this for several rounds.

**The same fault also existed in the 26.1.2 build, for a different reason.** NeoForge's JarJar keys
nested libraries on `group:artifact` and ignores the *classifier*, so `lwjgl-zstd:natives-windows`
and `lwjgl-zstd:natives-linux` collide and only one survives. On the user's Linux machine it kept
the **windows** jar, producing the identical `Failed to locate library: liblwjgl_zstd.so`. Log
evidence: only `lwjgl-lmdb-natives-windows.jar` and `lwjgl-zstd.jar` were loaded out of the six
shipped. Merging the natives into each library's own jar fixes both targets, since there is then one
artifact per library and no classifier collision. Both builds now carry the merge step.

**1. Terrain invisible with "Use sodium threads" ON — explained by the above**

Confirmed by A/B: world renders with voxy removed, and renders with voxy installed if
**Video Settings -> Voxy -> Use sodium threads** is turned OFF.

`MixinChunkJobQueue` swaps Sodium's chunk-build `Semaphore` for `SemaphoreBlockImpersonator`, backed
by voxy's `MultiThreadPrioritySemaphore`. This runs whenever a voxy *instance* exists -- turning off
voxy *rendering* does not disable it, which is why the render toggle changed nothing and misled the
first few rounds of diagnosis. With it active Sodium builds no chunk meshes, so terrain never
appears while block outlines and the minimap (both world-data, not meshes) still work.

Checked and NOT the cause: the `Semaphore` call sites are byte-identical between Sodium 0.8.13 and
0.9.1 (`acquire()V`, `availablePermits()I`, `release(I)V`, `tryAcquire()Z`), and `Block` implements
all four. So the mismatch is in behaviour, not shape -- still to be found.

**2. Vanilla fog wall hid the LoD terrain — FIXED**

The 26.x `MixinFogRenderer` did two things; the NeoForge `ViewportEvent.RenderFog` port only did the
first:

* conditionally push environmental fog out (`useEnvironmentalFog`)
* **unconditionally** set `renderDistanceStart/End = 999999999`

1.21.1 splits these by `FogRenderer.FogMode`: `FOG_TERRAIN` is the render-distance fog
(`start = far - f, end = far`), `FOG_SKY` the environmental one. The handler now pushes FOG_TERRAIN
out unconditionally and keeps FOG_SKY configurable.

**3. Freeze when toggling voxy rendering — FIXED**

The Sodium config screen drives `voxy$createRenderer()` twice for one toggle (the `RENDER_RELOAD`
flag and the option's own post-change runner), and voxy threw `IllegalStateException: Cannot have
multiple renderers`. It now tears down any existing renderer first. Upstream logic, not a port bug.
